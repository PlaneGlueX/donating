## Local setup (done 2026-09-24)
- **`Playtest.bat`** (repo root, 2026-10-04; the owner: "a batch file that makes playtesting the server easy access for me so i dont have to have you work on it to have everything working when turning on the server"): double-click for a menu (P play = start everything and open the Minecraft Launcher, S start, X stop, R restart, I status, K rebuild the pack and resend it to everyone on, L the log in its own window, C console commands over RCON, M the launcher, Q quit), or `Playtest.bat play|start [1G|2G]|stop|restart|status|pack|log|cmd "<command>"|launcher` (exit code 0/1; Claude can use it too). The logic is `tools\playtest.ps1` (ASCII only: PowerShell 5.1 reads a BOM-less .ps1 as ANSI). A start checks the jars (downloads.json; asks before fetch.ps1 downloads anything), rebuilds DonatingPhone.jar when a file under plugin\ is newer than the jar (only while the server is stopped: never replace a running plugin's jar) and the pack when anything build-pack.js reads is newer than the zip (MTVehicles' credits.txt is left out: it's rewritten at every start), starts the server and the pack server through start-server.ps1, waits for "Done (" in server\console.out.log, and reports the start: Skript's summary, script errors (Skript logs them at INFO: "Line N: (file.sk)" with the message on the next line), every ERROR line up to "Done" except the internet checks (Paper's version check, Mojang's key, PlaceholderAPI's list: they fail when the PC starts the server before its network is up). The server is found by its command line (`java ... -jar paper-*.jar`), not by server.pid (stale after a reboot); states stopped / starting / ready / stopping ("Stopping server": /stop or the local /restart). Windows Terminal is the default console: closing the Playtest window ends only the menu (checked: the server's java has its own hidden console), so it says so and Q offers to stop the server. Stop waits for a start to finish and offers a forced kill only after stop-server.ps1's 90 s. The javaw command line (the client's login token) is never read: Minecraft is found by its window title. A running server whose plugin jar or scripts are newer than its start says "R (restart) loads it" (status and P/S). Skript warnings print the same "Line N: (file.sk)" as errors (only the color differs, lost in console.out.log): with "All scripts loaded without errors." present they're reported as warnings. log4j also starts a new latest.log at midnight while the server runs (the log window tells that from a restart by the "[bootstrap] Running Java" first line). Get-Players returns an empty array for nobody online (`return , [string[]]@(...)`: a bare empty array becomes $null on return) and $null only for RCON down. Never let a called script's Write-Output reach a function that returns a bool (pipe it to the screen): PowerShell returns every output line too, and a non-empty array is true. Tested in a scratchpad sandbox (55 checks: the functions loaded from the script; the start report against real and fixture logs, staleness, states, the menu with keys fed in, a failing and a passing plugin build, the log window across rotations, midnight and split lines, the download prompt with a fake fetch) and on the real server (a cold start: plugin and pack rebuilt, ready in 76 s; status; cmd; restart in 90 s; a console stop seen as "stopping").

- Lag (owner, 2026-10-28: "check whats making the server and players lag, if you can make a command in game that can fix this when it gets laggy"): the cause was **spark's background profiler** (built into Paper, on by default): on Windows it has no async-profiler, so its Java sampler dumps every thread ~100 times a second, and each "ThreadDump" safepoint freezes the server until every thread reaches it, which took 1-3 s while DonatingPhone's city scan workers were busy (found with `jcmd <pid> VM.log output=file=... what=safepoint=info`: 12,654 safepoints in 100 s, the slowest 2.6 s to reach, matching the 2.6 s ticks to the millisecond; spark itself can't see it, the main thread just waits). `pluginssparkconfig.json` `"backgroundProfiler": false` (needs a restart; `spark profiler cancel` stops it at once): with the scan running, 4 ms a tick, 29 ms the worst in 10 s, against 115 ms and 2-5 s spikes before. It also explains the earlier 100-730 ms spikes near the Donut Shop. The scans also wait on `PhonePlugin.serverBusy()` now (average > 25 ms or any tick over 50 ms in the last 100) and keep 2 chunks in flight, not 4. Not the cause: GC (one 200 ms pause in 3 min), mob spawning (spawn_mobs false), new terrain (the jailbreak world's flat generator moved with it: each dimension's `data/minecraft/world_gen_settings.dat`). **`/lag`** (lag.sk, donating.staff): the tick time (SkBee `average tick time`) and TPS, entities by type, the 3 busiest chunks, the scans' state; **`/lag fix`**: cancels spark's profiler, removes dropped items that aren't ours (duffels `donating_duffel` and items with `donating_id` stay), arrows and XP orbs, runs copSweep and carSweep, cancels a running city/road scan (it starts over when run again: run scans with nobody on), logged to lag.log. Profiling without uploading: `spark profiler start [--only-ticks-over N]`, `spark profiler stop --save-to-file`, then `tools/node/node.exe tools/sparkread.js <file> [minPct] [self]` (protobuf: ThreadNode 3 = flattened StackTraceNodes, 5 = root refs; StackTraceNode 3 class, 4 method, 8 times, 9 child refs); `spark tickmonitor --threshold-tick 100` logs slow ticks; `jcmd <pid> VM.log output=file=... what=gc=info,safepoint=info decorators=time` for GC and safepoint stalls (`VM.log disable` after) (the server's pid from server.pid, never jcmd -l). Skript reloads freeze the server 0.8-9 s (traps.sk the worst): never reload during play.

- Computer-use tips (verified 2026-09-24):
  - Sneak + click (2026-11-04): the click tool's shift modifier is too short for the server to see a sneak, and a hold in another tool races the click. `powershell -NoProfile -ExecutionPolicy Bypass -File tools\mc-sneakclick.ps1 -Button right|left` holds shift and clicks in order, and sends nothing unless Minecraft is the front window. Clicks and moves through a set cursor position don't turn the camera (raw input); use `minecraft:rotate`, or mouse_event with MOUSEEVENTF_MOVE. The client discards the first mouse movement after a menu closes.

## Workflow
1. **Local test server first**: set up Paper 26.1.2 in `.\server` with the same plugins and configs planned for Minehut. Java 25 is portable in `tools\jdk25` (start-server.ps1 and build-plugin.ps1 use it; tools\downloads.json).
2. **EULA**: ask the owner before setting `eula=true`; it means agreeing to Mojang's EULA.
3. **Run it**: start the server in the background with `-Xms1G -Xmx1G` to match Minehut, so lag shows up early. Read `logs/latest.log`.
4. **Console access**: turn on RCON locally (`enable-rcon=true`, random `rcon.password`) and run commands with a small RCON script. Never port-forward RCON.
5. **Skript loop**: after each change run `/sk reload <script>`, read the output, and fix until it loads clean. Test one script at a time.
6. **Testing**: bot players and playtests; see the Testing section below.
7. **Resource pack testing**: serve the pack zip with a local web server and point `resource-pack` in server.properties at it.
8. **Deploy**: give the owner an exact list of files to upload through Minehut's File Manager (DEPLOY.md: plugins, configs, console commands). Never copy local-only settings (offline mode, RCON) to Minehut. Keep DEPLOY.md current when a plugin, config file or setup command is added.
9. **Downloads**: most plugins can be downloaded from GitHub/Modrinth/Hangar. SpigotMC usually blocks scripted downloads, so ask the owner to grab those by hand.
